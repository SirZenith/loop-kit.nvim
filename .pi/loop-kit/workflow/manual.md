本文件描述「人工验收 runbook」的标准（默认标准；项目可在 `loop/workflow/manual.md` 覆盖）。

把「需要真机 / 人工确认」的验收项写成一份**可照做、可勾选、可留证**的操作手册。
它不是实现文档，也不是验收报告：你只写验收指南，**不执行验收、不填写结果**。

# 适用场景

编排器在两种情况下会拆出人工验收条目，并调用本步骤补全 runbook：

- spec 阶段声明 `VERIFICATION_LEVELS` 含 `device` / `manual`：本轮无法自动验收，拆一条**创建即
  blocked、`deps` 为空**的人工验收条目；原条目改为 blocked 并依赖它（依赖反转）。
- spec 声明 `DEFERRED_LEVELS`：自动档验收通过后，拆同样的 blocked 人工验收条目；原条目 blocked
  并依赖它并落 finalize 断点，人工项 `loop-cli done` 后原条目走 finalize-only（只归档 + done）。

原条目的实现文档是主要素材，重点读其中的「验收标准」「验证方式」「延后档位」；
没有实现文档时，以条目 `desc`、代码现状和拆分原因为准，信息不足就明说缺什么。

# 文档位置与命名

编排器已经写好骨架并把路径交给你，**不要换路径、不要新建第二份文档**。
命名形如 `docs/<模块>/<时间戳>-<slug>-manual-<新条目id>.md`；模块沿用原实现文档。

# 必含小节

保留骨架的 YAML 头与以下结构，只把占位内容改写成具体、可执行的步骤：

- `## 1. 背景与完成定义` —— 原条目、拆分原因、原实现文档；什么算验收完成。
- `## 2. 前置条件` —— 环境、设备、账号、数据、证据目录等，逐项可勾选。
- `## 3. 验收步骤（逐项勾选）` —— 每一步一行 `- [ ] **S<n> <名称>**`，下面写：
  - `操作：` 具体到可以照做的命令 / 点击路径 / 输入数据；
  - `预期：` 可观察、可判断的结果（界面状态、日志、数值范围、错误提示）；
  - `实际：______` 与 `证据：______` **必须留空**，由执行人填写。
- `## 4. 结果记录` —— 表格：步骤 | 环境/设备 | 预期 | 实际 | 证据 | 结论；
  有测量值、日志或性能数据时，补「数值 / 日志记录」表（项目 | 期望 | 实测 | 误差 | 结论）。
- `## 5. 验收结论` —— 未勾选的 `- [ ] PASS` / `- [ ] FAIL`，以及验收人、日期、环境、失败原因填写位。
- `## 6. 完成后回写` —— 勾选完成 → 提交文档与证据 → 执行 `loop-cli done '<新条目id>'`；
  结论为 FAIL 时保留条目为 blocked，记录原因，必要时另开修复条目。

# 步骤写法

- 步骤按执行顺序编号，**一步只验证一个可判断的点**；不要把多个设备、多个场景塞进同一步。
- 先写「准备 / 基线确认」，再写主流程，最后写边界、异常与回归。
- 预期必须是可观察的事实，不写「工作正常」「体验良好」这类无法判定的词。
- 涉及真机（`device`）时，明确设备型号、OS / 固件 / 软件版本、连接方式、烧录或安装步骤；
  涉及人工（`manual`）时，明确验收人需要看什么、在哪里看、如何截图或导出日志。
- 需要重复执行或参数化的步骤，给出示例输入与期望输出；不要只写「测试各种情况」。
- 取材不足时给出「待补充」并说明缺什么，不要编造命令、界面文案或判据。

# 结果与证据

- **绝不预填任何结果**：所有「实际 / 证据 / 实测 / 结论」保持空白，PASS / FAIL 保持未勾选。
- 不写「已验证」「通过」等结论性文字；你写的是指南，不是验收报告。
- 证据位要写清形式：截图、录屏、串口日志、`dmesg`、性能数字、导出的文件路径等。
- 结果表与步骤一一对应；步骤增删时同步增删表格行。

# 与实现文档的关系

- 不重复实现方案与代码细节；需要背景时用一句话引用原实现文档。
- 原实现文档的「延后档位」与验收标准是步骤的主要来源；逐项落到本 runbook 的 S1、S2…。
- 原实现文档的自动档验收标准已经由自动验收覆盖，不在这里重复；只写留给人工的部分。

# 边界

- 只写 runbook：**不实现代码、不执行验收、不填写结果、不改任何条目的 `status`、不提交**。
- 不改 YAML 头的 `task_id` / `module` / `tag` / `verification_levels` / `deferred_levels`；
  这些由编排器按拆分结果回写。
- 不执行 `git push` 或任何远程写操作；不派发子 agent、不切换模型。
- 不删除骨架中的安全提示与「留空」要求；需要调整结构时保持同样的信息量。

# 输出契约

最终回复只给一句话摘要：runbook 相对路径 + 步骤条数 + 覆盖了哪些人工档位（`device` / `manual`）。
不需要机器行；素材不足时明说缺什么，不要编造步骤或验收结果。
