本文件描述自动提出新需求（补货）的规则（默认标准；项目可在 `loop/workflow/refill.md` 覆盖）。

LOOP 中已没有 `pending` 或 `doing` 的条目。你的任务**只提出需求，不实现需求**。

# 输入

- `TARGETS.md`（含「任务分类（tag）」）、项目根 `CONTEXT.md`、项目内其它产品/设计文档。
- 补货规则：`loop/workflow/refill.md`（存在则遵循，否则用下面的默认检查项）。

# 新增条目（**必须用 CLI**）

    loop-cli add --title "<标题>" --tag <分类> --origin refill [--desc-file <路径|->] [--deps '#1','#2']

- `--origin refill` **必须显式传**：标记该需求不是人手提出的，便于事后审计。
- **`desc` 首段必须自成摘要**：流程判定只读 `desc` 的前若干字（`judge.stateChars`，缺省 256）。
  头一段必须在长度内说清「这条任务要达成什么」。
- **`desc` 按 Markdown 写**（`gitea` / `github` 会把它原样作为 issue 正文渲染；`jira` 只作
  最小 ADF 纯文本）：一句话摘要开头、空行分段、`- ` 列要点、反引号包代码。**不要写成一整段
  长文**。多段描述用 `--desc-file`（`-` 读 stdin）；`--desc "…"` 里的反引号会被 shell 当命令替换。
- `--tag` 取自 `TARGETS.md` 的「任务分类」。
- `id` 由 CLI 顺序分配；`deps` 缺省为 null，确有先行依赖时才用 `--deps`，**不要引用尚未存在的 id**。
- 不要手改 `LOOP.json`；自检用 `loop-cli list [--eligible]`、`loop-cli validate`。

# 默认检查项

1. **功能完整性**：`TARGETS.md` 指明的功能集是否已全部实现；没有就推进功能集。
2. **用户体验**：现有功能组合是否满足 `TARGETS.md` 的体验目标。注意各小功能各自合乎目标、
   合在一起未必。
3. **视觉目标**：功能集完整、体验良好后，按 `TARGETS.md` 的视觉目标调整与美化界面。
4. **代码健康**：是否有明显重复模式可提取为公共组件；是否有过长函数值得拆分。
5. **其它**：文档、测试、工具链是否留有明确待办。

若以上都没发现问题，明确说明「无需新增」，不要为了凑数造需求。

# 边界

- 只新增需求条目，**不实现**任何需求、不改已有条目的 `status`。
- 除需求条目外不修改其它文件（引用文档只写引用，不创建文档）。
- 不提交（编排器负责提交与状态收尾）；不执行 `git push` 或任何远程写操作。

# 输出契约

最终回复给出简短 brief：检查了哪些方面、新增了哪些条目（或为何无需新增）。
