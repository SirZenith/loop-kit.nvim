本文件描述「验收」标准（默认标准；项目可在 `loop/workflow/verify.md` 覆盖）。

在提交之前，判定本次实现是否达到可提交的标准。你只读、不改代码。

# 输入

- 目标条目及其 `desc`、`doc`（绝对路径原样，其余相对路径相对项目根——即 `loop.config.json` 所在目录）。
- 本次改动范围（提示词会给出 `git status` / `git diff` 摘要，勿自行猜测范围）。`shared` 下只含本任务写集内的路径，其它任务的在飞改动已隐藏，不要据此判断回归；`worktree` 下给出本树全量改动（不再隐藏，与全量提交一致）。
- 测试结果：能跑就跑（规则见 `docs/workflow.md` 的「测试与验证档位」）。
- `TARGETS.md` 与实现文档的「验收标准」小节。

# 通过条件（**全部满足**才算通过）

- 功能符合实现文档与 `TARGETS.md` 提出的要求。
- 实现能通过所有测试；可自动化而未自动化的，按「人工核对与未实测项」处理。
- code review 关注点全部通过：正确性、边界情况、安全隐患、可维护性。

# 验证手段档位

按优先级从高到低，档位名固定五个（验收标准中的标注必须用这些词）：**单测** / **假 DOM** /
**渲染比对** / **真机** / **人工**。**单测 / 假 DOM / 渲染比对** 在纯 TUI 会话下即可完成，
是默认路径。

# 人工核对与未实测项

- 验收标准中出现「人工核对 / 人工验证」的条目时，**不得**据此判通过。
- 处理方式三选一：换成可自动执行的断言；确实无法自动化的（**真机** / **人工** 档）拆成
  独立条目并置 `blocked`（在 `desc` 写明「哪一项留给人工、为什么」）；或明确排除出本轮范围
  并在报告中说明。
- 完成 1) 2) 3) 之后，本条目按**剩余项**判定，**可以判通过**，不因存在需人工的项而卡住循环。
- 报告中**必须列出「本条目中未经实测的验收项」清单**；为空是合法结果，但不可省略。

# Code review 清单

- 正确性：逻辑正确、边界与失败路径被覆盖。
- 安全性：输入校验、注入、权限、敏感信息不泄露。
- 健壮性：错误处理得当，不留未处理异常。
- 可维护性：与既有模式/命名一致，无明显重复。

# 判定

- 独立判定，不向用户提问；任一条件不满足即不通过，**不允许提交与后续步骤**。
- 产物：简短的**通过 / 不通过**结论 + 逐条理由（引用文件、测试、命令）；不通过时给最小修改建议。

# 被复用时的行为（返工复判）

提示词可能带上一次验收的 `sessionID`（带历史启动）。**不要重新全面取证**：先看历史里已读过
的文件、已跑过的命令、上次的否决理由；聚焦「上次不通过的点」逐条核对是否修复、是否引入新
问题；上次通过的部分不必复验（除非本次改动触及）。仍需独立判断，严格度不变。首验没有历史
时按常规完整取证。

# 边界

- 只做验收与自查：**不修改代码、不提交、不改 `status`、不派发子 agent**。
- 不执行 `git push` 或任何远程写操作。

# 输出契约

最终回复首行必须是：

    VERDICT: PASS

或

    VERDICT: FAIL

需要人工介入时（真机 / 人工档且无法自动化）另起一行 `NEEDS_HUMAN: true`。
机器行缺失或无法解析 → 编排器视为 FAIL（保守方向）。
