本文件描述「功能实现」的标准（默认标准；项目可在 `loop/workflow/code.md` 覆盖）。

测试已经写好后完成实现，使测试与 typecheck 通过。

# 测试

本标准同时覆盖「先写测试」：实现前先建测试（红），实现中转绿。规则的完整版见
`docs/workflow.md` 的「测试与验证档位」小节；要点：

- 位置与命名沿用项目既有约定；无约定时与被测代码就近放置。
- 验收标准里标注**单测 / 假 DOM / 渲染比对**的条目，至少对应一个可执行断言；**先让新测试
  失败（红），再由实现使其通过（绿）**。
- 标注**真机 / 人工**或**没有档位标注**的条目：不得为其编造断言，在最终回复里回报。
- 除非测试本身有 bug、或新功能使旧测试失去意义，不得修改或删除既有测试；「测试步骤」之外
  确需修改测试时，单独作为一次提交并在提交信息中注明原因。

# 输入

- 实现文档（`doc` 字段，绝对路径原样、相对路径相对项目根——即 `loop.config.json` 所在目录；
  新布局在 `docs/<模块>/`，旧布局在 `feature/`）的「方案」与「验收标准」。
- 已写好的测试。
- 项目实现标准（若 `loop/workflow/code.md` 存在，从其规定）。

# 流程

- 以已写好的测试为目标实现功能，**先让测试失败（红）再由实现转绿**；不得为了通过而改坏业务逻辑。
- 复用项目既有的模式、命名与风格；改动范围贴合实现文档的方案。
- 除测试本身有 bug、或新功能使旧测试失去意义外，不得修改或删除既有测试。

# 验证

- 能跑测试就跑测试，能跑 typecheck 就跑 typecheck，并在最终回复里报告命令与结果。

# 提交与边界

- **不提交**：`git commit` 由编排器在验收通过后执行。改动留在工作目录。
- 不改条目 `status`；不派发子 agent；不执行 `git push` 或任何远程写操作。
- 实现受阻或方案不可行时，明确回报「哪一步卡住、为什么、建议」，不要留半成品。

# 返回摘要

- 改了哪些文件（路径）；
- 跑了哪些测试 / typecheck 与结果；
- 未决假设与风险（尤其与实现文档不一致之处）。

# 输出契约

可用下面这行给出建议的提交主题（编排器会校验并组审计 body，规约见 `docs/workflow.md`）：

    COMMIT: <Conventional Commits 主题行>

缺省时编排器用 `feat: <title> (#<id>)`。
